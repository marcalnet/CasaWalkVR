# CasaWalk: prompt for Claude Code

Paste everything below the line into Claude Code, running in an empty folder on the Mac (e.g. `~/Projects/CasaWalk`). Work in Plan mode first and approve the plan before any code is written.

---

## Goal

Build **CasaWalk** (first called Sweet Home VR; renamed at the user's request), a simple VR viewer for Meta Quest that opens **Sweet Home 3D (.sh3d)** files directly, with no conversion step. It should also open OBJ (plain, or zipped with MTL and textures) and GLB. It replaces the discontinued SketchUp Viewer for Quest for one job only: looking at a home model as a scale model, then walking through it at real 1:1 scale.

Headsets (decided with the user, the same as BRINK Traveler supports): Quest 3, Quest 3S, Quest 2 and Quest Pro. Quest 3 / 3S is the main target; Quest 2 and Quest Pro set the performance floor. Quest 1 is not supported (see phase 9 under "Working style").

Out of scope: editing the model, collaboration, accounts and scenes. Measuring and drawing are in scope (phase 17), but nothing they make is saved: a measurement or a drawing lasts until you leave the home, and the Photo button keeps it in a picture.

## Platform decision (already made; don't revisit)

- **WebXR web app** running in the **Meta Quest Browser**, built with **three.js**. Don't build a native Unity or Android app: no developer mode, no sideloading. The same web app may later also be packaged as an installable app (a PWA) without a rewrite, so keep it portable: the file readers and geometry code stay free of the page (`sh3d.js` already runs in Node), and browser-specific code (file picking, storage, saving, downloads, pairing) stays in few, clearly named modules.
- Plain ES modules and an import map, with **no build step**. Vendor every dependency into `/vendor` (three.js core plus the addons used, `fflate` for unzipping, `three-mesh-bvh` for fast raycasting) so nothing loads from a CDN at runtime.
- WebXR needs a **secure context (HTTPS)**. Host on **GitHub Pages**. Create the repo and enable Pages with `gh`, after asking me for the repo name. A plain `http://192.168.x.x` server on the Mac will **not** run WebXR on the Quest.
- The same URL must work on the Mac's desktop Chrome or Safari as a 2D preview (an orbit-controlled view of the model), so I can check that a file parses before putting the headset on.

## Getting files onto the Quest (decided)

1. **Primary: Dropbox.** I save the .sh3d into Dropbox on the Mac.
   - ~~"Open from Dropbox" button (the Dropbox Chooser)~~: never given an app key, and removed in the code audit's clean-up (A4, Nov 2026): a pasted Dropbox link does the job (below), and the Chooser would have been the one script loaded from another site.
   - **"Open from link"** field for pasted Dropbox shared links. Rewrite `www.dropbox.com` to `dl.dropboxusercontent.com` and force `dl=1`, keeping `rlkey`. This workaround is unofficial, so handle failure gracefully. Checked on the Quest 2: a Dropbox link pasted from WhatsApp opens fine, so the Chooser was never needed.
   - **Links from storage services** (asked for by Quest 3 testers; `js/links.js`). The browser can only download a file from another site when that site allows it (CORS), so each service needs its own route. All of them are unofficial except the Drive API, and every failure gets a plain message:
     - **Google Drive:** go through the official Drive API v3 (`files/{id}?alt=media&key=…`), with a browser API key set in `config.js` as `googleApiKey`. The key is limited to the Drive API and to the site's address, so the request sends the page's origin as referrer (`strict-origin`); every other request sends none. Google refuses its plain download address (`drive.usercontent.google.com`) to other websites: it answers 403 whenever the request carries `Sec-Fetch-Site: cross-site`. Older links pass their `resourcekey` in the `X-Goog-Drive-Resource-Keys` header. Without a key, Drive links explain the other ways in.
     - **OneDrive (personal):** the share id is `u!` plus the base64url of the share link (or the `redeem` value of an expanded link). Get an anonymous guest token from `api-badgerp.svc.ms`, the same step OneDrive's own web page takes for visitors who aren't signed in. Then read `my.microsoftpersonalcontent.com/_api/v2.0/shares/{id}/driveitem` and download its short-lived `@content.downloadUrl`. Both hosts allow other websites. No account is involved, and only the share link is sent.
     - **GitHub:** rewrite `github.com/…/blob/…` to `raw.githubusercontent.com`.
     - **Never possible from a web page:** OneDrive for work or school (SharePoint), iCloud Drive, Box, WeTransfer and MEGA. Recognise them and say so straight away. Folder links of every service get a "share the file itself" message. A sign-in page that arrives instead of a file (a link that isn't public) is detected and explained.
     - **The way round for any link that can't be opened:** on the headset, download the file in a browser tab and use Open file. On a computer, open the file and use Send to my Quest.
2. **Fallback: device file picker** (`<input type="file">`) for files already in the Quest's Downloads folder (e.g. downloaded from dropbox.com in the Quest Browser).
   - **Known Quest Browser bug:** files with uncommon extensions picked through `<input type=file>` can fail with `ERR_ACCESS_DENIED` when read through a blob URL. Read the file with `await file.arrayBuffer()` straight away and never create a blob URL from the picked `File`. If reading still fails, show: "Quest Browser blocked this file type. Rename it to .zip and try again". Accept `.zip` everywhere `.sh3d` is accepted, since a .sh3d is a zip.
   - Don't set a restrictive `accept` attribute.
3. **Recent models:** cache the last 5 loaded files (bytes, name, date) in IndexedDB, so reopening a model is one tap.
4. No Mac companion app. AirDrop can't target a Quest, and Android File Transfer is no longer maintained.

## SH3D format: implement from this spec

A `.sh3d` file is a ZIP archive. Since Sweet Home 3D 5.3 it contains a **`Home.xml`** entry, which is the only part to parse. Ignore the Java-serialised `Home` entry. If `Home.xml` is missing, say: "Re-save this file in Sweet Home 3D 5.3 or later."

All lengths are in **centimetres** and all angles in **radians**. Plan coordinates are x right and y down. Build 3D in cm as (x, elevation, planY), then scale the root by 0.01 to get metres. This is the same axis mapping Sweet Home 3D uses internally (Java3D, y up).

**Content references.** Attributes `model`, `icon` and `image` name ZIP entries, either a single entry like `"4"` or a folder entry like `"4/model.obj"` with its `.mtl` and textures beside it. Detect a model's format by magic bytes, not by name:
- `PK` = nested zip (unzip it and find the .obj, .dae, .3ds or .glb inside)
- `glTF` = GLB
- `<?xml` containing COLLADA = DAE
- `0x4D4D` = 3DS
- otherwise OBJ text

Resolve MTL and texture paths relative to the model's folder through a `LoadingManager.setURLModifier` that serves in-memory blobs. If a model is missing or broken, draw a unit box in its place.

**Sweet Home 3D's model defaults** (added 24 Nov 2026; `js/obj-defaults.js`; facts read from Sweet Home 3D 7, cited, no code copied):
- **Built-in materials.** An OBJ that names a material no `.mtl` defines gets it from Sweet Home 3D's built-in table (134 names, in its `OBJLoader`, after Java 3D's `DefaultMaterials`): its catalogue windows, with no `.mtl`, use `white` for the frame and `flltgrey` for the glass. A `.mtl` that defines the name always wins. `d` is the opacity; illum 1 or less means no highlight.
- **Window panes.** Sweet Home 3D makes glass see-through by the part's name, not its material: a part whose name starts with `sweethome3d_window_pane` (with `_on_hinge_` and `_on_rail_` panes) is shown at half opacity when its material is opaque (`ModelManager`, `updateShapeNamesAndWindowPanesTransparency`). A material that already has its own opacity keeps it; a material the pane shares with the frame is copied for the pane only; `sweethome3d_window_mirror` stays opaque. This holds for every format (the name of the part or a group above it). The panes are transparent like any glass (no depth writing) and merge into one material per colour.

**Elements to read:** `home` (has `wallHeight`), `environment` (`groundColor`, `skyColor`), `observerCamera`, `level`, `pieceOfFurniture`, `doorOrWindow`, `furnitureGroup` (recurse; children hold absolute coordinates), `light` (render as furniture and ignore the light sources), `wall`, `room` (with `point` children), `texture`, and `material`. Ignore labels, dimension lines, polylines and the compass.

**Visibility:**
- Skip items whose `visible="false"`.
- Skip items on a level whose `viewable="false"`.
- Colours are ARGB hex strings, e.g. `FF808080`.

**Furniture placement.** Copy this exactly; it is Sweet Home 3D's own `ModelManager` logic.

1. Normalise the model:
   1. Translate the model's bounding-box centre to the origin.
   2. If `modelRotation` (9 floats, row-major 3×3) isn't identity, apply it. Then, when `modelCenteredAtOrigin` is true (the default), re-centre on the rotated bounding box.
   3. Scale non-uniformly so the bounding box becomes 1×1×1.
2. Scale to (`width` × (−1 if `modelMirrored`), `height`, `depth`).
3. If `pitch` or `roll` is non-zero, pre-multiply by `rotZ(−roll) · rotX(−pitch)` and re-centre. The effective height is then the rotated bounding-box height.
4. Rotate by `rotY(−angle)`.
5. Translate to (`x`, `elevation` + effectiveHeight/2 + levelElevation, `y`). The `elevation` attribute is relative to the piece's level.

**Furniture colours and materials:**
- A piece `color` overrides the diffuse colour of all its materials.
- `<material name=… color=…>` children override only the material with that name.
- If `modelFlags & 1`, use `DoubleSide`; otherwise `FrontSide`.

**Walls:**
- Bottom = `level.elevation − level.floorThickness`, except on the lowest level, where the bottom is `level.elevation`.
- Top = `level.elevation + height`. If `height` is absent, use `home.wallHeight`. Walls can slope through `heightAtEnd`.
- Thickness is centred on the start→end line. With `a = atan2(yEnd−yStart, xEnd−xStart)`, the **left** side is offset by `(sin a, −cos a)·t/2`.
- Apply `leftSideColor`/`leftSideTexture` and `rightSideColor`/`rightSideTexture` per face, and `topColor` to the top.
- Texture `width`/`height` are the tile size in cm, so UVs in cm with repeat = 1/size.
- Joins: where `wallAtStart`/`wallAtEnd` is set, extend the wall by thickness/2 − 1 mm. Proper mitring can come later.
- Round walls (`arcExtent` ≠ 0): approximate with about 12 straight segments. Circle centre: `d = −tan(θ)·chord/2`, with `θ = (π − arcExtent)/2`, or `−(π + arcExtent)/2` if |arcExtent| > π. The centre is the chord midpoint + d·(cos φ, sin φ), with `φ = atan2(xStart − xEnd, yEnd − yStart)`.

**Door and window openings.** Cut a rectangular hole wherever a `doorOrWindow` is roughly parallel to a wall and its centre lies within thickness/2 + depth/2 of the wall axis.
- The opening covers a fraction of the piece: horizontally from `wallLeft·width` to `(wallLeft + wallWidth)·width` across the piece's width; vertically from the top down, starting `wallTop·height` below the piece top and spanning `wallHeight·height`.
- Defaults: wallLeft 0, wallWidth 1, wallTop 0, wallHeight 1.
- Project the opening onto the wall axis to get [u0, u1].
- Build each wall as rectangular prism cells: sweep along u and subtract the opening intervals. This gives reveals for free and avoids hole-touching-edge triangulation failures.
- Ignore `cutOutShape` (arched openings) for now.

**Rooms:**
- Floor polygon at the level elevation (or 0 without levels), one-sided facing up, using `floorColor`/`floorTexture`.
- Ceiling at `level.elevation + level.height` (or `home.wallHeight`), one-sided facing **down**, so the scale model can be seen into from above.
- Respect `floorVisible` and `ceilingVisible`.

**Ground:** a rectangle 3 m larger than the model on every side, at −0.5 cm, in `groundColor`.

**Start point:** `observerCamera` x and y give the default walk-in position. The facing yaw in three.js is `π − yaw`.

## Other formats

- **OBJ:** a single `.obj`, multiple picked files, or a `.zip` holding obj, mtl and textures. Units default to Auto (largest dimension > 100 → cm, otherwise m), with a cm / m / mm / in override. Sweet Home 3D's own OBJ export is in cm.
- **GLB/glTF:** metres. Compressed files open too (phase 15, added at the user's request): **Draco** and **meshopt** geometry are decoded by three.js's own decoders, vendored and loaded only when a file declares the extension (`gltfExtensions` in `js/formats.js`; Draco runs in two workers, meshopt on the page). **KTX2** (Basis Universal) textures can't be decoded under the security policy: the transcoder three.js ships builds functions from strings at run time (Emscripten's embind), which needs `unsafe-eval`. So the loader uses each texture's ordinary fallback image when the file has one; a file that requires KTX2 opens with plain surfaces in its own colours, and the status line says its KTX2 textures can't be shown yet. Real KTX2 support would need a transcoder built without run-time code generation, or one running in a worker served as its own file (decision for the user).

## Performance (Quest 2 is a phone GPU)

- After loading, bake world transforms and **merge geometry by material** (`BufferGeometryUtils.mergeGeometries`), deduplicating materials by colour, map and opacity. Aim for under 150 draw calls. **Plain colours share one draw call** (stage B3): an opaque, untextured Lambert material with no glow folds into one material per layer, storey and side, its colour stored in each vertex (`isPlainColour` in `js/optimise.js`); textured, see-through, glowing and ceiling materials keep their own (the ceilings' light lift reads their colour). The heavy test home went from 193 draw calls to 34, Pond House from 30 to 14. `?nofold` keeps every colour its own material, to tell fold bugs apart.
- Build a `three-mesh-bvh` bounds tree on the merged meshes; all raycasts (pointer, teleport, floor-following) must use it.
- Use `MeshLambertMaterial`, or Phong only where a model specifies shininess. One hemisphere light and one directional light. Use foveation (`renderer.xr.setFoveation(1)`) and a framebuffer scale of 1.
- **Time of day** (added at the user's request): Morning (the default, on the page and in the headset), Noon, Sunset, Night, in the VR menu and the 2D page's Display section (with Shadows as a switch), remembered. At sunset and night the bulbs of the home's light pieces (`lightSource` elements) are drawn as glowing spheres with soft halos; no real light sources are added. The sun direction comes from the home's compass (north direction and latitude, radians in Home.xml) on an equinox day: morning = solar 9:00, noon = solar noon, sunset = sun 5° above the horizon, night = a dim moon with a warm fill as if lamps were on. The sun turns with the scale model, so light always enters through the same windows. Noon without shadows keeps the original look. Skies (gallery, walk mode, 2D background) follow the time. **The light is calm and true to the file's colours** (the user's choice, 25 Nov 2026, after a beta tester found colours oversaturated; the cause was the presets, not the colour handling): near-white sun and more, paler sky fill, so whites stay white and shade lifts (a white wall in shade about L* 75 against 88–90 in sun); sunset is a low peach sun with the lamps on, no longer orange. The values are the Graphic Designer's (`PRESETS` in `js/lighting.js`).
- **Shadows** (optional, off by default; added at the user's request, replacing "no shadows"): one 2048 shadow map from the sun, rendered only when something changes (`shadowMap.autoUpdate = false`): loading, changing the time, or moving, turning or zooming the scale model. Walking costs only the shadow lookup. Glass (transparent, opacity < 0.9) does not cast, so sun comes in through windows; ceilings do, so with ceilings on, rooms are lit by the sun only through windows. With shadows on, the fill light is 0.9× and the sun 1.6×, so shadows read. Switching it on recompiles every material, a visible pause on a heavy home: since 26 Nov 2026 the headset's switch says so first ("Shadows …", drawn before the pause) and settles once the pause is over (`xr.shadowsBusy`); Depth shading shows its bake's percentage the same way. Both stay off by default, two switches (the Lead's decision on the Builder's measurements). Backlog, before either may default to on: an incremental or worker bake, a vertex budget with an honest "too large to shade" state, and shaders compiled at load.
- **Anti-aliasing:** MSAA on the XR framebuffer (`antialias: true`). No post-process or temporal anti-aliasing: the user found that it flickered in SketchUp Viewer. Texture shimmer is reduced with mipmaps and 8× anisotropic filtering instead.
- Show the triangle and draw-call count on the 2D page. If the model exceeds about 1.5 M triangles, warn but still load.
- **One base for what is drawn in the headset** (code audit, A5): every drawn card, board, key and label makes its canvas and texture through `js/canvas-card.js`; one sphere round the eyes (`js/veil.js`) serves the teleport fade, the move between layers and the photo flash, each asking for its colour and opacity, the strongest shown; and the interface lives on its own three.js layer (`INTERFACE_LAYER` in `js/photo.js`, put there by `XRExperience.hideFromPhotos`, rechecked before every photo and viewfinder frame), which the headset's camera shows and a photo's or the viewfinder's camera does not, so nothing is hidden and shown again for a photo. The app's raycasters see every layer (each cast names what it may hit).
- **One model service** (code audit, stage B1; no behaviour changed; `js/model-service.js`, no page code, tested in Node): files or a link in, a finished model out. It reads (`openFiles`), merges (or not, `?nomerge`), drops the older of two opens, frees the model shown when the new one is ready (or first, in the headset), and checks and downloads links (storage services, the size limit, the plain-words errors), saying each step through one status callback. `js/main.js` shows what it returns: where the model stands, its lamps, the headset and the lighting, Recent. Opening homes inside VR (C2) and projects will call the same service.
- **The page's parts** (code audit, stage B2; no behaviour changed): `js/main.js` keeps the 2D view, loading and the order things start in; the rest of the page is split by job into `js/page/`: the files card (`files-card.js`), Send to my Quest and Receive (`send.js`), the Enter VR button (`enter-vr.js`), the welcome and dropping files (`welcome.js`), and the build label with offline use (`updates.js`). Each part starts from one `init` that `main.js` calls where it always set that part up, so the page starts in the same order as before.
- **Development switches** (code audit, A4; `js/dev.js`): words in the page address, never in the menus or settings: `?test` (the browser tests; `window.__casawalk`, the test hooks, exists only then), `?hands` (the bare-hand tuning card), `?stats` (fps and draw calls in the headset), `?nomerge` (skip the merge), `?nofold` (merge, but keep plain colours apart), `?sw` (the service worker on plain http). Nothing else reads the address's switches, and only `js/device.js` reads the browser's name (the headset's own browser; a Quest 2); a test checks both.
- **The budget, checked** (code audit, A3): a model may cost **100 draw calls and 1,000,000 triangles** after merging (`CONFIG.budget`; the gallery, the interface and the hands take about 50 more draw calls, within the ~150 above). `tests/budget.test.js` measures the example and sample homes (they must fit: 30–40 draw calls) and the **heavy test home** (`examples/heavy-home.sh3d`, made by `scripts/make-heavy-home.js`, `npm run heavy-home`; not offered on the page: open it with `?model=examples/heavy-home.sh3d`). The heavy home has three storeys of 24 rooms, each with a detailed sculpture, dense plants, a shelf of books in six colours and furniture painted in 36 colours (whole pieces, and single materials of a piece), plus textures as Sweet Home 3D homes have them (parquet, stone and tiled floors, wallpaper on the top storey, upholstered armchairs, a marble pedestal: six generated images, two at 2048 px, about 60 MB of graphics memory with their mipmaps): about 970,000 triangles and **34 draw calls** since stage B3 (193 before; the Node test and the browser agree). The test also prints each home's textures and their estimated graphics memory. It fits the budget since B3; a test keeps it at 40 draw calls at most. **`?stats`** on the page URL shows a small line below your view in the headset: frames per second and the last frame's draw calls and triangles, both eyes together, everything drawn (development only, never in photos).

- **Depth shading** (added at the user's request, after SketchUp Viewer's ambient occlusion; headset only, off by default, remembered): white walls lose their edges when lit evenly. `js/depth.js` adds, with one multiply in the Lambert/Phong shader and one shared on/off uniform (no recompiling, no post-process pass, nothing that can flicker):
  - a side-light term from the model-space normal, so faces pointing different ways always differ slightly;
  - a per-vertex factor baked once per model: walls, floors and ceilings are cut along a regular 30 cm grid (convex cells, fan-triangulated, so gradients are even along every edge), then 32 short rays (0.6 m) per vertex against one BVH of the whole model except glass. Furniture blocks rays but is not baked itself (tried: three times the preparation time for a barely visible gain).
  - The bake runs in slices from the render loop (12 ms per frame on the page, 4 ms in the headset) and shows a percentage. Measured on the Mac: about 2 s for a 76,000-triangle flat, adding about 30,000 triangles.
  - Switches: the page's bottom bar and **Depth** in both headset menus.

## Safety (added in the pre-release audit)

A model file and a pasted link are untrusted input: the viewer will be shared, and people will open files from forums.

- **No outside requests from a model.** The loaders' URL modifier (`EntryStore`) serves only the file's own entries (`mem:`), embedded `data:` URIs and `blob:` URLs made from the file's bytes. Any other URL written in an MTL, glTF, COLLADA or 3DS file is replaced by a white pixel and counted; the status line reports how many were ignored.
- **Archive limits.** Before unpacking, the declared sizes are summed: over 1 GB or 50,000 entries (including nested model archives, which share one budget) the file is refused with a clear message.
- **Links.** `js/links.js`: only `https:` (or same-origin) links are downloaded, with a 500 MB cap, `credentials: 'omit'` and no referrer. `?model=` opens by itself only for a same-origin address; a link to another site is placed in the link field and waits for a click.
- **Page.** Content Security Policy in `index.html` (`default-src 'none'`, scripts from `'self'` plus the import map's hash, `'wasm-unsafe-eval'` for the vendored glTF decoders (WebAssembly only, never JavaScript `eval`), workers only from the page itself (the service worker, `sw.js`) and `blob:` URLs (three.js builds the Draco workers from the vendored decoder), connections to `https:` only), `referrer` set to `no-referrer`, and no HTML is ever built from file names or file content.
- **Parser.** Number attributes that are missing, NaN or infinite fall back to their defaults; impossible character references are left as written.
- **Memory.** Textures above `CONFIG.maxTextureSize` (2048) are shrunk after loading. Once the textures have loaded, the unpacked files and their blob URLs are freed.
- Accepted limits: a hostile file can still make the tab slow or crash it (huge geometry, a slow regular expression in Home.xml, an image that decodes to a huge bitmap). GitHub Pages cannot send headers, so framing by another site cannot be forbidden (`frame-ancestors`).
- **When something goes wrong in the headset** (the safety net, code audit stage A1; `js/safety.js`, pure and tested). Each headset frame runs inside it (`XRExperience.frame`). A lone script error shows a calm card in front of you, over everything, the layer curtain included ("Something went wrong. ← Back returns to the page. The Meta button always leaves VR."), for 6 s, and the app goes on. Five errors within 2 s (an error every frame): the frame's work stops, the card says "Returning to the page…", and the session ends 1.5 s later. Uncaught errors and rejected promises on the page count the same while in VR (outside VR they stay in the console). Back on the page, the status line says what happened (the error in short, and "reload the page"). A slow loop of errors ends it too (10 within 30 s), and so does any error during a move between layers (no half-done state). The graphics context being lost (the headset taking the graphics memory back) ends the session with its own message; when the browser gives it back, the page draws again without a reload (tested in headless Chromium) and the message clears. While Meta's menu covers the app (the session's `visibilityState` is not `visible`, read at the start too), no input is read (Apple Vision Pro's pinch included), a held model is let go and an aim or pull is dropped, the sound and vibration stop, and nothing of yours stays drawn frozen: hands, controllers, the orb, a held tool, the wrist menu and the tool fan are hidden until it is shown again (a store check, Input.4).

## Experience and controls

**2D page (home screen)**
- Name (decided with the user): "CasaWalk VR" wherever someone meets the app (browser tab and bookmark title, page header with a small "VR", README, link previews) and "CasaWalk" wherever they are already using it (headset menus, photo file names). Tagline "Mi casa es tu casa", subtitle "Opens Sweet Home 3D files".
- Buttons: Open from Dropbox, Open from link, Open file, plus the Recent list.
- Live orbit preview of the model.
- One **Enter VR** button, shown only if `navigator.xr.isSessionSupported` says so (changed at the user's request from separate VR and AR buttons). Checked on the Quest 2: the Guardian boundary still appears in the VR view of an AR session.
- Use `local-floor` reference space.

**XR scale model mode** (on entering XR, like SketchUp Viewer's tabletop view)
- VR view: a gallery room (changed at the user's request from the plain showroom): dark oak floor with a pale rug, warm white walls with dark skirting, a charcoal feature wall, tall windows on both sides, a skylight, and large abstract canvases, under a soft gradient sky. A rectangular museum plinth **1.24 m high with 30 cm of table around the model, the same for controllers and bare hands** (the user's decision, 26 Nov 2026; until then 0.6 m and 20 cm with a controller, rising to the bare-hands plinth when only hands were tracked), its front edge 60 cm in front of the user (was 30 cm; moved back at the user's request, B6: you can't walk around in the gallery). The model rests 4 mm above the plinth top, never exactly on it, and the plinth top is drawn with a small depth offset: at the same height the floors and the plinth flickered through each other on the headset (z-fighting). The headset's clip planes are set explicitly (5 cm to 300 m). You look down at it as a 2 m tall person would (eyes at 1.89 m), so it is easy to look and point into the rooms: the head's real height is measured on entry, on Recentre and when coming back from walking, and the view is raised by the difference, so it is the same sitting or standing and whatever the headset's floor level is (changed at the user's request: a fixed 25 cm raise only worked when standing). Passthrough view: no room and no plinth; the view keeps its raised height (changed at the user's request, B6), so switching only changes the background and the model stays exactly where it was (except that it never sinks below the real floor, which matters only when seated).
- On entering XR (and when the headset is re-centred), the room and plinth are placed in front of where the user stands and looks, not at the floor origin.
- The model is scaled to fit about 1.2 m across and sits on the plinth; it turns on the plinth, which stays still.
- Thumbstick left/right rotates the model; up/down does nothing. **No zoom** (the user's decision, 26 Nov 2026): the model opens at one round scale per visit, the one chosen on arrival (for example 1:10 or 1:25), and keeps it; the plate shows that one scale. (Until then the stick zoomed ×0.5 to ×4 and settled on a round scale: B2 below.)
- Grip plus moving the controller grabs and moves the model, keeping it upright (yaw only). It can be lifted but never pushed into the plinth (or, off the plinth, below the floor).
- Each controller shows a laser ray. Pointing at the model shows a small person-height marker where the floor is; **trigger** enters 1:1 standing at that spot. ## Design principles (the user's rule for every interface)

The user asked that every interface follow Dieter Rams' ten principles of good design (number 8 is read as "consistent in every detail"). Here is what each means in this app, with "Experience and controls" and phase 17 as the cases:

1. **Innovative:** use what VR does that a screen can't (tools in the hand, real 1:1 scale, real measurements), instead of flat panels copied into 3D.
2. **Useful:** every feature helps someone look at, understand or communicate a home. Cut what doesn't.
3. **Aesthetic:** only well-executed things are beautiful: crisp text, one family of materials (graphite, aluminium, paper, the orange accent), smooth motion at full frame rate.
4. **Understandable:** self-explanatory. Instructions sit on the tools themselves; an illustrated guide and a first-time introduction teach by showing; no gesture without a visible hint.
5. **Honest:** true sizes and true scale (the plinth shows the real ratio, e.g. 1:50); no false precision (lengths to the centimetre); say plainly what can't be shown (KTX2 textures); no tricks to push upgrades.
6. **Unobtrusive:** the home is the subject. Interface appears when summoned (the fan on a look, the menu on a wrist) and goes away; calm sound.
7. **Long-lasting:** no fashionable effects; open standards (WebXR, glTF); nothing that depends on our server staying up.
8. **Consistent in every detail:** the same word, colour, sound and vibration for the same meaning everywhere (orange = the thing to press; one shutter sound); every state designed (empty, loading, error).
9. **Environmentally friendly:** light on the device: few draw calls, throttled extra rendering, an idle page at 2 frames a second, no servers, small downloads. On a headset that means battery and heat.
10. **As little design as possible:** read as the user reads it: no needless complication, and nothing pretending to be what it isn't. One way to do each thing, few options, good defaults. It does **not** mean bare minimalism here.

**Shared headsets** (the user's principle, 26 Nov 2026): several people use one headset, at different times. Aids stay present and quiet rather than disappearing once seen. Teaching is per VR session, short, and ends early on the action. What you see (the home's light and view) is remembered. Who you are (your height) starts fresh each session, except the main hand. In code: `scope` in `js/settings.js` ('remembered' or 'session': Height), the session store (`js/session-store.js`: the tips, the first tabs, the first-target ring), cleared at Enter VR (and, until build 215's B4, by **New visitor**).

**When principles pull apart, fun comes first** (decided with the user): this app needs mood, character and some decoration (the studio room, the ambience, tools with personality, small celebrations like the floating photo print), and that beats minimalism. Two limits stay: usefulness and honesty are never traded for fun, and decoration lives *around* a task, never on top of it (while you measure or draw, nothing distracts).

## Roadmap: hand-held tools (milestones)

Bare hands: a thumb tap starts a stroke and the next tap ends it; a thumb swipe left or right changes colour; a swipe back undoes (the hand's teleport is off while it holds a tool). Strokes live in the tools' annotations (model space); photos keep them; a dot too small to see leaves no stroke. A stroke ends by itself on a jump (a teleport's fade, stepping inside or back, a snap turn or a thumb step, the nib moving more than 30 cm in a frame), and with bare hands when the hand opens or is lost (the tester's review): it never draws a line across a jump or keeps running unseen. **Cost** (the tester's review): the stroke being drawn starts with buffers for 64 rings and doubles them when full, uploading only each new ring; finished strokes merge into one mesh per colour (at most four draw calls for all of them). The meter's lines (rods and end dots) are one mesh, rebuilt when a line comes or goes or the zoom changes; their labels are one mesh too, quads turned to you each frame over one shared picture (32 slots). 20 measurements and 20 strokes: 6 draw calls. The meter's beam allocates nothing per frame; with bare hands its undo is the holding hand's thumb swipe back, as the marker's. Not yet: the faint buzz while drawing beyond a tick every few points, the squeak while moving.
- **G. - **H. Ambience and sound.** Decided: relaxed, not a busy studio (voices pull attention, suggest other people in the room, and grate on a loop; calm suits client presentations).
